# Codex 多 Key 路由工具 · 施工计划

> 版本：v6.0 施工版  
> 建立时间：2026-09-21  
> 本文档是本次开发的唯一执行依据，开发过程中如需变更，先改本文档再改代码。

## 一、目标与交付物

新建独立工程 **Codex多Key路由工具**，以现有 `Codex官方本地模型工具` 为核心做多 Key 化改造，只按需并入 `AI网关切换工具` 的代码。

最终交付：

| 平台 | 产物 | 说明 |
| --- | --- | --- |
| macOS | 未签名 dmg（arm64） | 双击 dmg，把 .app 拖进「应用程序」即可用 |
| Windows | 安装包 exe（x64） | 双击安装，桌面/开始菜单出现图标，带卸载项 |

目标机器**不需要**安装 Python 或任何环境。两端共用同一份 Python 核心与同一套界面代码。

### 功能清单

1. 支持多个 Key，每个 Key 的模型自动拉取；每个 Key 可单独勾选要拉取的模型，没勾的不拉。
2. 多个 Key 出现同名模型时，每个模型可配置路由优先级，固定走优先级最高的那一个。
3. 全部功能做成可视化界面（四页：概览 / Key 与模型 / 路由优先级 / 设置）。
4. 支持开机自启动。
5. **官方模型继续走 ChatGPT 账号**（见第二节），不是所有模型都要 Key。

## 二、两条链路（核心设计）

### 官方链路（保持原样，不动）

- 官方模型请求原样转发到 `https://chatgpt.com/backend-api/codex`，用本机 Codex 的 **ChatGPT 账号登录态**，不经过任何 Key。
- 官方模型清单读取 Codex 自己的缓存 `~/.codex/models_cache.json`，校验后合并进 Codex 模型目录。
- 官方与 Key 同名时，**默认 Key 覆盖官方**（老逻辑不变），界面上可单独改回官方。
- `切回官方直连` 按钮保留，语义不变。

### Key 链路

- 每个 Key 独立配置：名称、密钥、上游地址、启停、顺序、模型白名单。
- 刷新时对每个 Key 依次执行现有的 `fetch_gateway_models` → `probe_gateway_model` → `resolve_gateway_manifest`，**拉取与生效逻辑本身不改**，只是从"单 Key"变成"多 Key 循环 + 合并"。
- 合并后每个模型名在 Codex 里只出现一次；默认按 Key 列表顺序取第 1 个勾选了该模型的 Key。
- **不做失败自动切换**：首个来源报错就原样返回，不换 Key 重试。
- 模型清单里不写任何密钥，router 运行时按归属取密钥转发。

## 三、技术选型（已冻结）

| 部分 | 方案 |
| --- | --- |
| 核心 | Python 3.12，**只用标准库**（沿用现有 zstd 外部解码器方案），两端一份逻辑 |
| 界面 | 纯 HTML + CSS + JS，无框架，一份代码 |
| 窗口外壳 | Go 语言一份，两端各一个薄文件：Windows 用纯 Go 调系统 WebView2；macOS 用 cgo 调系统 WKWebView |
| Windows 运行时 | 内嵌 `python-3.12.10-embed-amd64`（与老项目一致） |
| macOS 运行时 | 内嵌 python-build-standalone（arm64） |
| 构建 | 全部在 Mac 上完成：Windows 安装包用 Go 交叉编译，macOS 用 `hdiutil` 出 dmg |
| 端口 | 路由沿用 `127.0.0.1:8790`；管理界面/API 用 `127.0.0.1:8791`（可改） |

## 四、数据结构与接口

### keys.json（新增，UTF-8 无 BOM）

```json
{
  "version": 1,
  "keys": [
    {
      "id": "k1",
      "name": "主力账号",
      "api_key": "sk-...",
      "upstream_base_url": "https://api.example.com/v1",
      "enabled": true,
      "order": 0,
      "selected_models": ["kimi-k3", "glm-5.3"]
    }
  ],
  "model_priority": { "kimi-k3": "k1", "gpt-5.1": "official" }
}
```

`model_priority` 的值只允许两种：`"official"` 或某个 Key 的 id。

### local-models.json（沿用现有结构）

- 保持现有校验：slug 唯一、`local/` 前缀规则不变。
- 每项新增来源标记 `key_id`（不含密钥）。
- 官方模型部分继续由 Codex 缓存提供。

### 管理 API（本机 127.0.0.1:8791）

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | /api/state | 总状态：路由、Key、模型、设置、官方账号 |
| POST / PUT / DELETE | /api/keys | 增删改 Key |
| POST | /api/keys/{id}/test | 测试连接 |
| POST | /api/keys/{id}/refresh | 拉取该 Key 的模型 |
| PUT | /api/keys/{id}/models | 保存该 Key 的模型白名单 |
| PUT | /api/priority | 保存同名模型的归属 |
| POST | /api/router/refresh \| start \| stop \| direct | 控制路由 |
| GET / PUT | /api/settings | 自启动、端口、接管开关 |
| GET | /api/events | 最近事件 |

### router 改动范围

只改两处：manifest 支持多来源、`route_request` 按归属取密钥转发。官方分支、Responses→Chat 桥接、工具注册、reasoning carrier、zstd 处理全部保持原样。

## 五、编码兼容铁律（Windows / PowerShell / .bat 专项）

> 这一节是硬约束，任何一条不满足都算不合格。

1. **不使用 .bat 文件**。启动、停止、刷新全部由 Go/Python 原生进程完成，不经过命令行解释器。
2. 必须调用 PowerShell 时，统一走 `-EncodedCommand`（UTF-16LE + Base64），不把中文写进命令行参数。
3. **会被 Windows 解析的命令字符串一律纯 ASCII**：不写 .bat / .cmd / .ps1；命令行参数不含中文；PowerShell 只走 `-EncodedCommand`。运行时 Go 源码纯 ASCII；Python 源码统一 UTF-8 无 BOM（Python 3 默认按 UTF-8 解析，该前提已写入自动测试守护）。
4. Python 启动时强制 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8`，并对 stdio 做 `errors="replace"` 兜底；无控制台时 stdout/stderr 指向 devnull。
5. 所有配置文件、日志文件一律 **UTF-8 无 BOM**；写文件显式指定 `encoding="utf-8"`，不依赖系统默认编码。
6. 默认安装路径使用纯 ASCII：`%LOCALAPPDATA%\CodexMultiKey`，避免路径编码问题。
7. 不硬编码 `cp936`/`gbk`，也不依赖控制台代码页；界面文案走 HTTP/JSON，不走控制台。
8. Windows 侧用 Go 的 UTF-16 API 处理路径，Python 侧用 `os.fsdecode` 处理文件名。
9. 实测三种情况：中文 Key 名、中文用户名路径、CRLF/LF 行尾。
10. 打包产物中的文本文件（说明、配置模板）统一 UTF-8 无 BOM + CRLF（Windows）/ LF（macOS）。

## 六、分阶段实施（每阶段一个 Git commit）

1. **骨架与配置层**：建工程目录、从老项目拷入核心、写 `keys.json` 读写与旧配置迁移、单元测试。
2. **路由多 Key 化**：manifest 多来源、`route_request` 按归属取密钥、测试。
3. **清单合并与优先级**：多 Key 模型合并、去重、优先级解析、官方同名覆盖规则、测试。
4. **管理 API 与界面**：本地 API 服务 + 前端四页，按效果图实现。
5. **自启动**：Windows 注册表 Run 项、macOS LaunchAgent，沿用老项目实现。
6. **Go 壳**：两端窗口外壳，加载本地界面，支持无窗口后台模式。
7. **Windows 安装包**：Go 交叉编译安装器 + 内嵌运行时，产出安装 exe。
8. **macOS dmg**：组装 .app + `hdiutil` 出 dmg。
9. **文档与验收**：使用说明、端到端验收、编码兼容实测。

## 七、测试与验收

### 单测（只做必要项）

- 多 Key 读写与旧配置迁移
- 同名模型合并与优先级
- 模型白名单过滤
- 路由命中指定 Key
- 官方同名被 Key 覆盖，且可改回官方
- config.toml 写入失败回滚
- 自启动注册（mock）

### 端到端冒烟

- 起假上游，两个 Key 都有同名模型，验证走优先级第 1 的 Key。
- 验证官方模型请求仍是原样转发，且不带任何 Key。

### 打包验收

- 本机挂载 dmg 启动 .app，功能可用。
- Windows 安装包在 Windows 机器上双击安装、打开界面、加两个 Key、刷新模型，Codex 里官方模型与 Key 模型都能正常对话。
- 重启电脑后，后台服务自动起来（界面显示运行中）。

## 八、假设与默认值

- 界面以已确认的 4 张效果图为视觉基线。
- 新工程目录名 `Codex多Key路由工具`，应用显示名「Codex 多 Key 路由」，与两个老项目同级。
- macOS 只出 Apple Silicon（arm64）dmg；未签名首次打开需右键「打开」或到系统设置里放行。
- Windows 只出安装包 exe，不出便携 zip。
- 首次启动若检测到老工具配置，自动导入 Key 与已选模型，并提示停用老工具，避免两个程序同时改 Codex 配置。
- 本次只做多 Key 路由工具，不合并 8790/8787 两个代理；老项目的模型探测规则、官方缓存校验、配置回滚行为全部保留。
- 首版不做托盘图标：默认开机只静默拉起后台服务，需要界面时双击图标打开。
