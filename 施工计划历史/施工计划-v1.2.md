# Codex 多 Key 路由 v1.2 并发拉取、原生 /responses 直通与图标加底

## 概要

本轮修 4 个已定位问题：多 Key 拉取串行太慢、gpt-5.6-sol / luna 选不了推理强度、gpt-5.6-terra 明明接通却显示「未接入」、Dock 图标没有白底；另加一个交互：概览页「模型来源」点 Key 展开已接入模型。版本 1.2.0，Mac 与 Windows 用同一份核心逻辑。

## 根因（已用真机日志与上游实测确认）

1. **并发**：`resolve_multi_key_manifest()` 里 `for key in enabled:` 逐个 Key 拉 `/models`，N 个 Key 就是 N 倍等待。实测上游 5 并发 `/models` 全 200、总 0.8s，6 并发对话请求全 200，没有硬限流。
2. **sol / luna 没有推理强度**：上游在 chat 模式明确报错 `Function tools with reasoning_effort are not supported for gpt-5.6-sol in /v1/chat/completions. To use function tools, use /v1/responses or set reasoning_effort to 'none'.`。探测必须开 function 工具，只能一路降级到 `none`，于是目录里 `supported_reasoning_levels` 只剩 `['none']`，前端就不显示滑块。网关 `/v1/responses` 实测支持这些模型带工具 + medium/high/xhigh/max，且返回的 reasoning item 带 `encrypted_content`。
3. **terra 显示未接入**：chat 探测第二轮多带了一个 `parallel_tool_calls: false`，terra 返回 200 但正文为空，被 `_has_assistant_text` 判为不兼容，日志 `no_compatible_tool_roundtrip`；模型没进清单，请求回落到 `route=official`。去掉该字段后实测稳定通过。
4. **Dock 图标无底**：源图 `icon.png` 是 1254×1254 RGBA 透明底，派生出的 icns 自然没有底。用户提供的 `icon圆角.png` 是同样尺寸、带纯白圆角底。
5. **模型来源不能展开**：`state()` 的 `keys[]` 只有 `included_count`，前端没有按 Key 分组展示已接入模型的能力。

## 改动方案

**1. 多 Key 并发拉取（含限流回退）**
- `resolve_multi_key_manifest()` 的逐 Key 拉取改线程池并发，固定 3 并发；结果顺序按 Key 顺序固定，与完成先后无关。
- 某 Key 撞到 429 / 5xx / 超时 / 连接错误时，等其余 Key 跑完再对它单独串行重试一次（带退避间隔）；仍失败只写该 Key 的 `error`，不影响其他 Key。
- 同一个 Key 内部的模型探测保持串行，不并发打同一个 Key。
- 日志 `multi key discovery concurrent key=... ms=...` 与 `multi key discovery retry serial key=... reason=...`。

**2. Key 模型走网关 /responses 原生直通**
- 拉模型时读 `/models` 每条记录的 `supported_endpoint_types`：声明 `openai-response` 才走一轮式 `/responses` 探测（function 工具 + `tool_choice:"required"`，拿到 `function_call` 即通过，并从高到低试出可用推理档位）；只声明 `openai` 的维持现有 chat 桥接、不多发请求；字段缺失时才实探兜底。
- 探测通过的模型记录打标 `wire_api: "responses"`，`supported_reasoning_levels` 按最高可用档位展开，sol / luna 的推理强度滑块随之出现。
- 转发：`wire_api: "responses"` 的模型把请求发到 `上游地址 + /responses`，只改写 `model` 为上游模型 ID，headers 本地清洗 + 换 Authorization；流式与非流式字节直接透传，不做协议转换；上游报错原样回传状态码与正文。
- 保留两个前置拦截：`generate:false` 预热请求、缺全量上下文的 `previous_response_id`。
- chat 探测第二轮去掉多余的 `parallel_tool_calls`，修掉 terra 的误判；单 Key 旧链路同步升级同一套探测顺序。

**3. 应用图标加白底**
- 应用图标源按 `icondock.png`（成品白底圆角卡片，生成时抠掉卡片外白边）→ `icon圆角.png`（合成纯白圆角底）→ `icon.png` 的顺序回退，派生 macOS 全套 icns 与 Windows exe / 桌面 / 托盘 ico。
- 透明版 `icon.png` 单独派生菜单栏剪影与界面 logo，菜单栏不出现白块。
- 三张源图都缺时用默认图标，不让打包失败。

**4. 概览页「模型来源」点击展开**
- 每行 Key（含官方行）可点击展开，列出当前已进路由清单的模型与接入方式标签，再点收起。
- 「Key 与模型」页「接入方式」列按 `wire_api` 显示「原生直通」/「Chat 桥接」，状态列显示「已接入 Codex」。

## 接口与数据变化

- `local-models.json` 模型记录新增可选 `wire_api: "responses"`，缺省即现有 chat 桥接，旧清单无需迁移。
- 管理端 `state().models[]` 新增 `wire_api`。
- 新增 `fetch_gateway_catalog()` 返回模型 + 端点能力，原 `fetch_gateway_models()` 保留为薄封装。
- `keys.json` 与 Codex provider 配置不改。

## 测试与验收

- 单测：探测三条链路（声明支持 / 声明不支持 / 字段缺失）、并发结果顺序、429 单 Key 串行重试、直通改写 model 与两个前置拦截、`wire_api` 透出管理端、图标源映射与缺图回退。
- 真机联调：真实网关 + 两个真实 Key 刷新后 sol / luna 出现完整推理档位、terra 显示已接入且不再走 official；用 Key 模型跑一次真实请求，日志出现 `wire=responses route=local`；claude 仍为 chat 桥接；并发刷新无 429，并人为制造限流验证回退生效。
- 图标验收：Dock 与 Windows 图标有白底圆角，菜单栏剪影无白块。
- 回归：`python3 -m unittest discover -s tests -q` 与 launcher / installer 的 `go test ./...` 全过。

## 假设与默认

- 并发度固定 3，不做配置项；同 Key 内探测串行。
- 上下文窗口沿用 `discovery.defaults.context_window`（默认 200k）与按模型覆盖机制；网关不暴露上下文上限、给超大 `max_output_tokens` 也不报错，这轮不探测上下文长度。
- 图片输入按现有默认开启，直通原样透传，不额外降级。
- 刷新模型列表会重建 manifest，直通标记随之刷新，无需手工迁移。
